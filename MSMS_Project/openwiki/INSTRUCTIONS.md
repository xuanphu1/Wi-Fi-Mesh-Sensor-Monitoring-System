Đây là firmware hệ thống giám sát cảm biến môi trường phân tán, viết bằng C với ESP-IDF 5.2.5 và FreeRTOS. Mỗi thiết bị ESP32 có thể hoạt động như mesh node hoặc mesh root. Node đọc dữ liệu từ các cảm biến được gắn vào từng port, tạo telemetry JSON và gửi liên tục tới root qua kết nối TCP. Root nhận dữ liệu đồng thời từ nhiều node, đóng vai trò bộ tập trung dữ liệu và chuyển tiếp từng JSON frame sang gateway bên ngoài qua UART.Hãy tạo tài liệu kỹ thuật chi tiết dựa trên source code hiện tại; source code, CMake, Kconfig và sdkconfig là nguồn sự thật. Không dựa vào các mô tả cũ trong README nếu chúng mâu thuẫn với code. Không xem các thư mục external_examples hoặc managed component là logic ứng dụng chính.Kiến trúc chính của dự án:- main/: entry point app_main(), khởi tạo NVS, SPIFFS, button, I2C, OLED, UART gateway, battery monitoring, performance monitoring, network, RTC và storage.- component/core/: trạng thái toàn cục và logic nghiệp vụ, gồm DataManager, FunctionManager, BatteryManager, TimeManager, StorageManager, PinManager, SystemPerformance, ProcessingDataMesh và UartToGateWay.- component/ui/: ButtonManager, MenuSystem và ScreenManager cho màn hình OLED SSD1306, menu điều hướng và hiển thị trạng thái/dữ liệu cảm biến.- component/sensors/: SensorTypes định nghĩa kiểu dữ liệu; SensorRegistry đăng ký driver; SensorConfig cung cấp lớp wrapper để khởi tạo, đọc và giải phóng cảm biến.- component/drivers/: driver phần cứng như BME280, BMP280, AHT10, HTU21D, DHT11, MH-Z14A, PMS7003, ADS1115, DS3231, SD card, PCF8574, SSD1306 và I2C.- component/network/: InternetManager điều phối chế độ mạng; WifiManager cung cấp Wi-Fi AP/STA và captive portal; MeshManager quản lý ESP-Mesh-Lite và TCP transport; WebSocketHandle và WebConfigWifi phục vụ giao tiếp/cấu hình mạng.- component/utils/: ErrorCodes và các tiện ích dùng chung.InternetManager quản lý các trạng thái INTERNET_MODE_NONE, INTERNET_MODE_WIFI và INTERNET_MODE_MESH. Firmware mặc định khởi động ở mesh mode với vai trò node. Khi đổi mode, cần mô tả rõ thứ tự dừng tài nguyên của mode cũ và khởi tạo mode mới.MeshManager đã sử dụng TCP, không còn dùng UDP cho telemetry. Kiến trúc TCP cần được tài liệu hóa kỹ:- MeshManager.c chỉ làm nhiệm vụ điều phối lifecycle, chuyển role và cung cấp public API.- mesh_network.c quản lý Wi-Fi bridge, ESP-Mesh-Lite và trạng thái topology.- mesh_tcp_transport.c sở hữu toàn bộ socket trong một FreeRTOS task duy nhất.- Ở node, task chờ node tham gia mesh, xác định IP root, mở một kết nối TCP lâu dài, gửi telemetry định kỳ và reconnect bằng exponential backoff cộng jitter khi mất kết nối.- Ở root, một listening socket nhận nhiều client socket. Một vòng select() duy nhất quản lý listener và tất cả node; không tạo một task riêng cho từng kết nối.- Mỗi client có TCP stream parser độc lập vì TCP có thể chia một JSON qua nhiều lần recv() hoặc gộp nhiều JSON vào một lần recv().- Mỗi frame là một JSON kết thúc bằng ký tự newline. Parser hỗ trợ LF, CRLF và loại bỏ frame vượt giới hạn.- Root nhận diện node bằng MAC trong JSON thay vì chỉ dựa vào IP, vì IP có thể thay đổi sau reconnect.- Frame hoàn chỉnh được đưa vào gateway queue private của MeshManager. UartToGateWay lấy frame qua public API rồi gửi JSON và newline tới gateway.- Khi chuyển role hoặc shutdown, chính transport task đóng listener, node socket và client socket để tránh race condition hoặc double-close.- Số client TCP chịu giới hạn bởi CONFIG_MESH_TCP_MAX_CLIENTS và CONFIG_LWIP_MAX_SOCKETS. Root luôn cần thêm một socket cho listener.Telemetry JSON hiện gồm các trường phiên bản schema, sequence, mesh level, MAC, timestamp, firmware version, danh sách lỗi và dữ liệu các sensor port. Hãy mô tả schema bằng ví dụ JSON, ý nghĩa từng trường, giới hạn frame, newline framing và đường đi dữ liệu từ sensor driver → SensorRegistry → telemetry builder → TCP → root queue → UART gateway.DataManager chỉ nên lưu trạng thái ứng dụng dùng chung. Socket, queue và chi tiết TCP transport thuộc quyền sở hữu của MeshManager, không phải DataManager. Đồng thời xác minh target chip từ sdkconfig thay vì chỉ dựa vào README.Ưu tiên tài liệu giải thích “tại sao” bên cạnh “làm thế nào”, nhất là lý do TCP root cần một listening socket cộng nhiều accepted socket, lý do phải có stream parser và lý do chỉ một task được quyền đóng/mở socket.
